Tumoro.org Talent Ratings Service API Documentation
Overview
The Talent Ratings Service is a critical microservice responsible for calculating, adjusting, and storing the real-time reliability score for every talent on the platform. The rating system is based on a weighted Base Score and adjusted by a dynamic K-Factor (Rating Adjustment Speed) to reflect the talent's true expertise over time.
Core Concepts and Persistence Strategy
To ensure scalability and fast reads of the most current data, the rating information is split across two collections, which is the most efficient approach for this type of time-series data:
TalentState Collection: Stores a single document per talent containing only the current, active metrics (e.g., $R_c$, $K$, $E$). This is used for all fast read/write operations.
RatingEntries Collection: Stores individual documents, where each document is a complete historical snapshot of a rating calculation and result.
Concept
Description
Base Score
The weighted average of performance across key components.
Current Rating ($R_c$)
The talent's current, most recent rating, stored in the TalentState document. Default: 400.
K-Factor ($K$)
The adjustment speed (percentage) applied to the rating difference. Stored in TalentState.
Engagement Count ($E$)
The total number of high-impact engagements used to determine the K-Factor tier. Stored in TalentState.

Rating Adjustment Formula
The New Rating ($R_{new}$) is calculated using the following adjustment formula:
$$R_{new} = R_c + K \times (BaseScore - R_c)$$

2. Business Logic: Calculation Details and Persistence
2.1 Base Score Calculation
The Base Score is calculated as a weighted average.
Weights Used (Normalized):
$W_{Interview} = 0.35$
$W_{FamilyTree} = 0.35$
$W_{Assessment} = 0.25$
$W_{Profile} = 0.03$
$W_{Spotlight} = 0.02$
Total Weight: $1.00$
$$BaseScore = \sum (Score_i \times W_i)$$
2.2 K-Factor Determination (Rating Adjustment Speed)
The K-Factor is determined by the talent's current engagementCount ($E$).
Engagement Count (E)
Rating Tier
K-Factor (K)
$E \le 10$
Tier 1: New Talent
$1.0$ ($100\%$)
$11 \le E \le 30$
Tier 2: Developing Talent
$0.5$ ($50\%$)
$E > 30$
Tier 3: Established Talent
$0.2$ ($20\%$)

2.3 Initial State and Persistence Logic
Initialization on Read (Mandatory for efficiency):
The service must implement "initialize-on-read" logic for the GET endpoint. If a TalentState document is requested but not found, the service must immediately create and persist it with the following defaults before returning the response:
currentRating: $400$
currentKFactor: $1.0$ (Tier 1 default)
engagementCount: $0$
lastUpdated: Current Timestamp
lastInputScores: Empty/Zeroed BaseScoreInput object
Update Persistence (Atomic):
The POST /update endpoint must use an atomic transaction or batch write to ensure consistency between the two collections:
Update TalentState: Write the new $R_{new}$, $K$, $E$, and lastInputScores.
Insert RatingEntry: Add the full historical snapshot document to the RatingEntries collection.
3. API Endpoints
3.1 Get Talent Rating (Current State and History)
Retrieves the current, active rating and can optionally retrieve the full historical record.
Detail
Specification
Endpoint
GET /v1/talent/{talentId}/rating
Authentication
Required (Internal Service Auth or Talent Read Scope).
Path Parameters
talentId: String (required)
Query Parameters
includeHistory: Boolean (optional, default false). If true, history is fetched from the RatingEntries collection.
Logic Flow (Core)
1. Initialization Check: Fetch TalentState. If not found, execute Initialization on Read (2.3). 2. Return the current state.
Success Response
200 OK (Always, if talentId is valid)
Response Body (Example)
Returns the TalentState object. If includeHistory=true, the response will also include a ratingHistory array of RatingEntry objects, ordered by timestamp descending.
Error Responses
401 Unauthorized

3.2 Trigger Rating Calculation and Update
This is the primary endpoint for updating a talent's rating based on a new performance record. This endpoint is responsible for all calculation and history logging.
Detail
Specification
Endpoint
POST /v1/ratings/update/{talentId}
Authentication
Required (Internal Service Write Scope).
Path Parameters
talentId: String (required)
Request Body
BaseScoreInput object (JSON)
Logic Flow
1. Retrieve current $R_c$, $K$, $E$ from TalentState. 2. Calculate $BaseScore$, new $K$, and $R_{new}$. 3. Increment $E$. 4. Execute Atomic Persistence (2.3): a. Update TalentState. b. Insert new RatingEntry history document. 5. Return the new TalentState.
Success Response
200 OK
Response Body
Updated TalentState object (JSON)
Error Responses
400 Bad Request (Validation failure), 500 Internal Error (Transaction/DB failure)

Example Request Payload (POST /v1/ratings/update/TMR-12345):
{
  "interviewScore": 85,
  "familyTreeScore": 70,
  "assessmentScore": 92,
  "profileQualityScore": 65,
  "spotlightPerformanceScore": 80
}
